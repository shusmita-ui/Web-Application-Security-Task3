# Cross-Site Request Forgery (CSRF) Attack Scenario

## 1. Vulnerability

Cross-Site Request Forgery (CSRF) is a web application vulnerability in which an attacker attempts to cause an authenticated user's browser to send an unintended request to a vulnerable application.

---

## 2. Target

**Application:** DVWA (Damn Vulnerable Web Application)

**Security Level:** Low

**Module:** CSRF

---

## 3. Normal Request

The password-change functionality was first tested normally.

A legitimate password-change request was generated by the application.

The request contained parameters associated with the password-change operation.

---

## 4. Request Capture

Burp Suite was used to intercept and inspect the HTTP request.

The captured request was examined to understand the parameters used by the password-change functionality.

---

## 5. Attack Scenario

The captured request was analyzed to demonstrate how a state-changing request could potentially be triggered without sufficient CSRF protection.

The testing was performed only against the local DVWA laboratory environment.

---

## 6. Observed Result

The password-change functionality accepted the request when the required parameters were supplied without adequate anti-CSRF protection.

This demonstrated the importance of protecting state-changing requests against unauthorized cross-site requests.

---

## 7. Impact

A successful CSRF attack may cause an authenticated victim to unintentionally perform actions such as:

- Change account information
- Change a password
- Modify application settings
- Perform other state-changing actions

9. Mitigation

CSRF can be mitigated using:

Anti-CSRF tokens
SameSite cookie attributes
Origin validation
Referer validation where appropriate
Re-authentication for sensitive operations
10. Anti-CSRF Token

A protected state-changing request should contain an unpredictable anti-CSRF token.

Example:

POST /change-password

The request should include a valid anti-CSRF token associated with the user's session.

The server should verify the token before processing the request.

11. SameSite Cookies

Cookies can use the SameSite attribute to reduce cross-site request risks.

Example:

SameSite=Lax

or, where appropriate:

SameSite=Strict
12. Origin and Referer Validation

For sensitive state-changing operations, the server can validate the Origin or Referer headers where appropriate.

This provides an additional layer of protection against unauthorized cross-site requests.

13. Re-authentication

Sensitive operations such as password changes can require the user to authenticate again before the operation is completed.

14. Validation

After implementing CSRF protection, a request without a valid anti-CSRF token should be rejected by the application.

This ensures that unauthorized cross-site requests cannot perform protected state-changing operations.

15. Conclusion

The CSRF testing demonstrated the importance of protecting state-changing requests from unauthorized cross-site actions.

Unpredictable, session-bound anti-CSRF tokens combined with appropriate cookie and request-origin controls can provide effective protection against CSRF attacks.

16. Disclaimer

All testing documented in this repository was performed against a controlled DVWA laboratory environment for educational and security testing purposes only.
